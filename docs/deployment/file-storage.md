# File / document storage — production limitation

## Current implementation

`backend/src/services/storage.service.js` implements `LocalStorageAdapter`: generated documents (invoice
PDFs, etc.) are written to local disk, rooted at `DOCUMENT_STORAGE_PATH` or `<cwd>/storage/documents` by
default. Path-traversal-safe (keys are resolved and rejected if they'd escape the root), atomic writes
(write-to-temp-then-rename), never statically served. This behavior is unchanged by Phase 11 — not a
regression, a pre-existing, correct implementation for a single-instance deployment.

## The limitation

Local disk storage only works correctly when:
- there is exactly **one** backend process/instance serving traffic, and
- that instance's disk persists across restarts/redeploys.

This holds for a single EC2 instance with PM2 in fork mode + 1 instance (see `ecosystem.config.js`) and
a persistent EBS volume. It does **not** hold for:
- **Render**: the filesystem is ephemeral and wiped on every deploy/restart — generated documents are
  lost. See [render.md](./render.md).
- **PM2 cluster mode / multiple instances**: a document generated by one process is invisible to another
  behind a load balancer, since each has its own disk.
- **Any future horizontal scaling on EC2** (multiple instances behind an ALB).

## What this phase does NOT do

Per the task's explicit instruction not to silently switch storage providers or add a cloud dependency
unless required: **no S3/object-storage adapter has been implemented**. The existing abstraction
(`storage.service.js` comment, lines 10-11) already anticipates this — any future adapter implements the
same four methods (`save`/`read`/`delete`/`exists`) and is swapped in at `container.js` with no caller
changes required elsewhere in the codebase.

## Future object-storage adapter requirements (not implemented)

When horizontal scaling or Render production use is actually needed, implement an adapter satisfying:
- Same interface as `LocalStorageAdapter`: `save(key, buffer)`, `read(key)`, `delete(key)`,
  `exists(key)`.
- Keys remain server-constructed only (as they are today via `document.service.js`) — never derived from
  user input, so no new IDOR/path-traversal surface is introduced by the storage layer itself.
- Private bucket/container (no public read access); access via signed URLs or server-side proxying only,
  matching the current behavior where authorization happens before any file read (see
  `docs/security/` — document access is tenant/vendor-scoped before storage is ever touched).
- Credentials (access key, bucket name) sourced from environment configuration, validated at startup the
  same way other secrets are (see `backend/src/config/env.js`), never logged.

## Interim guidance

Until an object-storage adapter exists: deploy on EC2 with PM2 in single-instance fork mode (the current
default in `ecosystem.config.js`) and a persistent EBS volume, or accept document loss on redeploy if
using Render for a demo/non-production environment only.
