# Tally Integration Handoff

This document is for the **external Tally/TDL integration team**. It gives everything needed to connect
a Tally/TDL deployment to this ERP so Tally can pull company, customer, product, and invoice data, and
trigger a sync, without the ERP needing a network path to reach Tally directly.

For the full endpoint reference (every field, every query parameter), see
`docs/api/tally-public-api.md` in this repository — this document is the shorter, practical quick-start.

## 1. What you will be given

- **ERP API base URL**: `https://<erp-domain-placeholder>/api/v1/tally/public` (your ERP contact will
  give you the real domain — never a value from this document).
- **An API key**: a string starting with `tk_live_`, generated by your ERP contact from the ERP's
  **Tally → Tally API keys** screen. It is shown to them exactly once at creation time — if it's lost, ask
  for a new one (rotation) rather than asking "what was it again," since the ERP cannot retrieve it either.
- **The scopes granted to your key** — your key may not have every scope listed below; ask your ERP
  contact which ones you were given.

No real API key appears anywhere in this document — the examples below use the placeholder
`tk_live_EXAMPLE_PLACEHOLDER_DO_NOT_USE`.

## 2. Authentication header

Every request must include:

```
X-Tally-API-Key: tk_live_EXAMPLE_PLACEHOLDER_DO_NOT_USE
```

There is no login step, no OAuth flow, no session/cookie — just this one header on every request.

## 3. Company endpoint

```
GET /company
```
```bash
curl -s https://<erp-domain-placeholder>/api/v1/tally/public/company \
  -H "X-Tally-API-Key: tk_live_EXAMPLE_PLACEHOLDER_DO_NOT_USE"
```
```json
{ "success": true, "data": { "companyName": "Acme Traders", "gstin": "27AAAAA0000A1Z5", "state": "Maharashtra", "stateCode": "27" } }
```
Requires scope: `tally:company:read`.

## 4. Customer endpoint

```
GET /customers?page=1&limit=50
```
Returns a page of the tenant's customers. See `docs/api/tally-public-api.md` for all filter parameters
(`search`, `status`, `from`/`to`, `sort`). Requires scope: `tally:customer:read`.

## 5. Product endpoint

```
GET /products?page=1&limit=50
```
Same shape and filters as customers. Requires scope: `tally:product:read`.

## 6. Invoice endpoint (list)

```
GET /invoices?status=ISSUED&from=2026-04-01&to=2026-04-30
```
Returns invoice summaries (number, date, status, grand total, GST applicability). Requires scope:
`tally:invoice:read`. Figures returned are always the ERP's authoritative, frozen values — never
recalculated from current customer/product data.

## 7. Single invoice endpoint

```
GET /invoices/:id
```
Returns full invoice detail: line items, computed tax breakup, and the customer/supplier snapshot exactly
as they were when the invoice was issued. Requires scope: `tally:invoice:read`. An invoice id that
belongs to a different ERP tenant, or doesn't exist, returns `404` either way — your key can only ever
see its own tenant's invoices.

## 8. Sync endpoint

```
POST /invoices/:id/sync
```
Triggers a sync of that invoice into the tenant's already-configured Tally instance (configured on the
ERP side, not by you). Requires scope: `tally:sync`. Safe to call more than once — an already-synced
invoice just returns its current `SYNCED` status with no duplicate action; a sync already in progress
returns `409`.

```json
{ "success": true, "data": { "invoiceId": "...", "status": "SYNCED", "voucherId": "...", "voucherNumber": "SALE-001" } }
```

## 9. Request/response examples

See `docs/api/tally-public-api.md` §"Endpoints" for a complete worked example of every response shape
above, plus every documented error code.

## 10. Error codes

| HTTP status | Code | Meaning |
|---|---|---|
| 400 | `VALIDATION_ERROR` | Malformed id, bad date/enum, pagination out of range |
| 401 | `TALLY_API_KEY_INVALID` | Key missing, malformed, unknown, revoked, or expired (deliberately indistinguishable) |
| 403 | `AUTHORIZATION_ERROR` | Key is valid but lacks the required scope for this endpoint |
| 404 | `NOT_FOUND` | Resource doesn't exist, or belongs to a different tenant |
| 409 | `TALLY_SYNC_IN_PROGRESS` / `TALLY_RETRY_LIMIT_EXCEEDED` | Sync-specific conflicts |
| 429 | `RATE_LIMIT_EXCEEDED` | Too many requests — back off and retry later |

The sync endpoint's `errorCode` field (inside a `200` response reporting a failed sync — see §8) can also
be `TALLY_UNREACHABLE`, `TALLY_TIMEOUT`, `TALLY_MALFORMED_RESPONSE`, `TALLY_REJECTED`,
`TALLY_COMPANY_NOT_FOUND`, or `TALLY_DUPLICATE_VOUCHER`. The last two are inferred from Tally's own
rejection message text (Tally has no structured error code for these) and are best-effort, not guaranteed
— report any misclassification you observe back to the ERP team.

**Response format is JSON only.** There is no XML response mode on this API, even though Tally itself
speaks XML on the ERP's outbound side (Phase 6). If your integration genuinely needs XML from a specific
endpoint, tell your ERP contact — do not attempt to request `Accept: application/xml`, it is not supported.

## 11. Pagination

`page` and `limit` query parameters; `limit` is capped (ask your ERP contact for the current cap if your
integration needs a specific page size). Always read `pagination.pages`/`pagination.total` from the
response rather than assuming a fixed page count.

## 12. Rate limits

Your key is limited independently of other tenants' integrations and of normal ERP user traffic — current
default is 120 requests/minute per key (your ERP contact can confirm the value actually configured in
their environment). A `429` response includes standard `RateLimit-*` headers indicating when to retry.

## 13. Retry behavior

- `GET` requests: safe to retry on a `5xx` or network error.
- `POST /invoices/:id/sync`: safe to retry at any time — it is idempotent (see §8).
- Do not retry a `4xx` without changing the request; retrying the same invalid input will not succeed.

## 14. Idempotency

The sync endpoint is naturally idempotent per invoice id — no `Idempotency-Key` header is needed or
supported for it. There is nothing else in this API with a side effect to make idempotent.

## 15. Security requirements (your side)

- Store the API key the way you would store any production credential — a secrets manager or encrypted
  configuration, never committed to source control, never logged in plaintext.
- If the key is ever exposed (committed to a public repo, logged, shared over an insecure channel), tell
  your ERP contact immediately so they can revoke it and issue a new one — revocation is immediate and
  irreversible, and no key can be "un-revoked."
- Use HTTPS only; the ERP will not accept the key over plain HTTP in production.
- Do not share one key across multiple unrelated Tally deployments if you want to be able to revoke one
  without affecting the others — ask for a separate key per deployment if that's your situation.

## 16. What this integration does NOT do

- No GSTN/government e-filing of any kind.
- No automatic GST acknowledgement or ARN generation — none of that is implemented anywhere in this ERP.
- No invoice creation/editing/cancellation from the Tally side — this API is read access to ERP data plus
  one action (triggering an existing sync), nothing more.

## 18. Phase 16 addendum: Tally Connector Bridge (separate from this Public API)

This document covers the Phase 13 **Tally Public API** (Tally/TDL → ERP, JSON, `X-Tally-API-Key`). Phase 16
adds a **completely separate** mechanism for the client bill-intake workflow: a Windows Tally Connector
authenticated with its own `X-Tally-Connector-Secret` credential, bridging the ERP's Tally Queue to a local
TallyPrime instance. It does not replace or extend this Public API — a Tally Public API key cannot be used
as a connector secret and vice versa (enforced and tested).

See `docs/integrations/tally-connector.md` for the full architecture, registration flow, job lifecycle,
retry/idempotency, security model, troubleshooting guide, and — importantly — the exact list of what still
needs to happen before a real TallyPrime instance can be used (this addendum, like the rest of this
document, has **not** been validated against real TallyPrime/TDL software).
